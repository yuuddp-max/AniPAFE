# 運営管理の初期データ取得の整理（2026-10-29）

運営管理で、対象年度の投票設定を個別に取得した後、同じ設定を含む年度一覧を再取得していた。年度一覧から対象年度の設定を取り出すことで、個別取得を1回削減した。概要・年度一覧・集計の取得は対象年度が分かった時点で並行して開始する。

管理者確認を通過してから管理データを取得する順序を維持し、対象年度の設定が見つからない場合はエラーとする。ヘッダーの年度と概要の年度の照合も維持する。投票や設定をリクエスト間でキャッシュする変更、DBの構造や権限の変更はない。

## 同条件での計測

変更前はコミット `0e4c769` の本番ビルド、変更後は同コミットに今回の変更だけを適用した本番ビルドを使用。Edge・PGlite・107作品の合成フィクスチャで集計キャッシュを生成後、PostgREST通信ごとに100msの遅延を加え、背景先読みを除外して各3回計測した。

| 指標 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 初期表示のDB通信 | 8回 | 7回 |
| 投票設定の取得 | 2回 | 1回 |
| 集計年度の表示確認まで（3回） | 558 / 550 / 545ms | 549 / 533 / 538ms |
| 同・中央値 | 550ms | 538ms |

通信の削減は3回とも確認した。表示時間の差は12msと小さく、ばらつきを含む少数回のローカル計測なので、体感速度や本番の短縮率は断定しない。

## 検証

- 今回の変更だけを反映した独立ディレクトリで本番ビルド・型チェックが成功。
- 初期通信のE2Eを3回実行し、通信7回以内・年度一覧の取得1回を確認。
- 関連E2E6件が成功。管理者以外の拒否、一覧の再試行、年度切り替え、明細のページ取得、CSV全件出力、画面遷移後の最新投票表示を確認。
- 利用中のNext.jsに同梱された `node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md` と[SupabaseのSELECT仕様](https://supabase.com/docs/reference/javascript/select)を確認。

上記の計測値はローカル検証の結果。本番の表示時間は別途測定が必要。
