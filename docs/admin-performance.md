# 運営管理の初期表示改善（2026-10-17）

## 原因と変更

`src/app/admin/page.tsx` は、初期タブが「投票集計」であるにもかかわらず、作品一覧・投票者一覧・全ログインユーザー・操作履歴を取得していた。作品一覧と投票者一覧では年度設定もそれぞれ再取得していた。また、これらと登録状況の読み込みが完了してから `loadTally` を開始していた。

- 初期表示は対象年度・年度一覧・登録状況・集計結果だけを取得し、集計と登録状況を並列実行する。
- 作品一覧・投票者一覧は各タブの初回選択時に既存の管理者限定APIから取得する。取得後はコンポーネントを保持し、タブ移動で選択年度・検索・編集中の状態を失わない。管理操作によるサーバー更新後は、表示対象年度のデータを再取得する。
- 操作履歴は新設の管理者限定 `/api/admin/audit` で取得する。最新30件・`private, no-store`・取得失敗時の再試行を維持する。
- 初期表示に不要な管理コンポーネントを `next/dynamic` で分割する。
- `src/app/admin/loading.tsx` を追加し、画面移動時に読み込み状態を表示する。認証・管理者判定は従来どおりサーバーで実行する。

## 比較計測

ローカルのNext.js開発サーバー、Edge、PGliteで実行。107作品・確定票なしの同一フィクスチャを使用し、コンパイル・集計結果の保存が済んだ後の `/admin` 再表示を比較した。全PostgREST通信に100msの待ち時間を加えている。

| 指標 | 改善前 | 改善後 |
| --- | ---: | ---: |
| DB通信数 | 13回 | 8回 |
| 遷移開始から集計年度選択欄の表示確認まで | 2,100ms | 1,527〜1,578ms |
| 初期HTMLレスポンス（未圧縮・開発用情報を含む） | 211,693 bytes | 122,580〜122,583 bytes |

改善前1回・改善後3回の計測で、時間は約25%、HTMLは約42%削減。これらは本番の実測値や大量投票時の速度保証ではない。初期表示に不要なテーブルの取得がなくなったことは通信ログと回帰テストで検証した。集計キャッシュがない場合は従来どおり再計算する。

性能計測とタブの遅延取得・年度保持・通信失敗時の再試行・操作履歴APIの401/403拒否は `tests/e2e/admin-performance.spec.ts` で再現できる。テスト用の通信計測と遅延設定はループバック専用の `tests/supabase-harness.ts` 内だけに存在し、アプリケーションからは参照しない。

```powershell
npx playwright test tests/e2e/admin-performance.spec.ts tests/e2e/admin-years.spec.ts tests/e2e/tally.spec.ts tests/e2e/historical-voter-links.spec.ts
npm run typecheck
npm run build
```

DBスキーマ・RLS・集計ルールの変更は不要。本番への反映と本番環境での速度確認は未実施。

## 回帰確認

関連E2Eは計10件を確認（性能・遅延取得2件、年度別管理3件、集計2件、過去投票者紐付け3件）。未ログイン/一般ユーザーの操作履歴取得拒否、管理者による再試行、年度別編集・取込・削除、集計条件の保持、CSV、原本保持、320〜1440pxの表示を含む。既存の管理タブ表示テストは、現行の6タブ・PCで3列2行の構成に合わせて更新した。

型チェック、`git diff --check`、本番用ビルドは成功。本番用ビルドは制限環境の `.next` ディレクトリ作成が `EPERM` で失敗したため、通常権限で同じコマンドを再実行し、終了コード0を確認した。
